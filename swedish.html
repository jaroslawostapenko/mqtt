Standarden för IoT-meddelanden

Bemästra MQTT-protokollet. Lättviktigt, effektivt och pålitligt meddelandesystem för Internet of Things. Byggt för instabila nätverk och miljöer med låg bandbredd.

Vad är MQTT?

MQTT (Message Queuing Telemetry Transport) är ett standardiserat meddelandeprotokoll (OASIS) för Internet of Things (IoT). Det är utformat som en extremt lättviktig publish/subscribe-meddelandetransport (publicera/prenumerera) som är idealisk för att ansluta fjärrenheter med en liten kodbas och minimal nätverksbandbredd.

Det utvecklades ursprungligen av IBM 1999 för att övervaka oljepipelines via satellitanslutningar, och har nu blivit de-facto-standarden för IoT på grund av dess effektivitet och tillförlitlighet över instabila nätverk.

Varför är det så populärt?

  • ⚡ Lättviktigt: Den minsta paketstorleken är bara 2 byte, vilket minskar nätverksbelastningen.
  • 🛡️ Pålitligt: Erbjuder 3 nivåer av Quality of Service (QoS) för att säkerställa leverans.
  • 🔄 Dubbelriktat: Möjliggör meddelanden mellan enhet-till-moln och moln-till-enhet.
  • 💾 Varaktigt: Kvarhållna meddelanden (Retained) gör att nya enheter omedelbart kan få det senast kända tillståndet.

Arkitektur och komponenter

MQTT-protokollet frikopplar avsändaren (publicisten) och mottagaren (prenumeranten) via en central komponent som kallas mäklare (Broker).

Mäklaren (Broker)

Hjärtat i systemet. Den tar emot alla meddelanden, filtrerar dem, bestämmer vem som är intresserad av dem baserat på prenumerationer och publicerar sedan meddelandet till alla prenumererande klienter. Populära mäklare inkluderar Mosquitto, HiveMQ och EMQX.

Publicist (Publisher)

En klient som skickar data (meddelanden) till mäklaren på ett specifikt ämne (topic). Till exempel en temperatursensor som publicerar data till home/livingroom/temp. Publicister behöver inte veta vilka prenumeranterna är.

Prenumerant (Subscriber)

En klient som registrerar intresse för ett specifikt ämne. När mäklaren får ett meddelande om det ämnet vidarebefordrar den det till prenumeranten. En klient kan vara både publicist och prenumerant.

Förstå ämnen (Topics)

MQTT-ämnen är hierarkiska strängar som används för att filtrera meddelanden. De använder ett snedstreck / som avgränsare. De är skiftlägeskänsliga.

Ämnesstruktur

Ett typiskt ämne ser ut så här:

myhome / groundfloor / kitchen / temp

Denna hierarki möjliggör specifik adressering av enheter.

Jokertecken för ämnen (Wildcards)

  • En nivå (+):
    home/+/temp matchar home/kitchen/temp men inte home/kitchen/fridge/temp.
  • Flera nivåer (#):
    home/# matchar allt som börjar med home, t.ex. home/kitchen/temp och home/garage/light/status. Detta måste vara det sista tecknet i ämnet.

Tjänstekvalitet (QoS)

MQTT erbjuder tre specifika tjänstekvalitetsnivåer för meddelandeleverans. Detta gör att utvecklaren kan välja rätt balans mellan omkostnader och tillförlitlighet för specifika meddelanden.

0

QoS 0

Högst en gång

Även känd som "Fire and forget". Meddelandet skickas en gång. Ingen bekräftelse förväntas. Om anslutningen bryts eller servern är upptagen går meddelandet förlorat för alltid.

Användningsfall: Periodisk temperatursensordata där missad data (en av hundra avläsningar) inte är kritisk.

1

QoS 1

Minst en gång

Garanterar att ett meddelande levereras minst en gång till mottagaren. Avsändaren lagrar meddelandet tills den får ett PUBACK-paket. Dubbletter kan uppstå om bekräftelsen går förlorad.

Användningsfall: Slå på en strömbrytare. Du vill definitivt att den ska slås på, och att det görs två gånger är acceptabelt.

2

QoS 2

Exakt en gång

Den säkraste och långsammaste nivån. Garanterar att meddelandet tas emot exakt en gång med hjälp av ett handslag i fyra steg. Detta förhindrar dubbletter.

Användningsfall: Banktransaktioner, faktureringssystem eller kritiska larm där dubbletter orsakar fel.

Exempel på implementering

MQTT har klientbibliotek tillgängliga för nästan alla programmeringsspråk (C, C++, Java, Python, Go, JavaScript, etc.).

Python (Paho-MQTT)

Standardbiblioteket för Python IoT-appar.

import paho.mqtt.client as mqtt

# Callback när anslutning upprättats
def on_connect(client, userdata, flags, rc):
    print(f"Connected with result code {rc}")
    # Att prenumerera i on_connect säkerställer 
    # att vi återprenumererar om anslutningen bryts
    client.subscribe("home/sensors/#")

# Callback när meddelande tas emot
def on_message(client, userdata, msg):
    print(f"{msg.topic}: {msg.payload.decode()}")

client = mqtt.Client()
client.on_connect = on_connect
client.on_message = on_message

client.connect("broker.hivemq.com", 1883, 60)
client.loop_forever()

JavaScript (Node.js)

Använder MQTT.js-biblioteket för asynkrona operationer.

const mqtt = require('mqtt')
// Anslut till en offentlig testmäklare
const client  = mqtt.connect('mqtt://test.mosquitto.org')

client.on('connect', function () {
  console.log("Connected!")
  
  // Prenumerera på presence-ämnet
  client.subscribe('presence', function (err) {
    if (!err) {
      // Publicera ett meddelande
      client.publish('presence', 'Hello mqtt')
    }
  })
})

client.on('message', function (topic, message) {
  // meddelandet är en Buffer
  console.log(message.toString())
  client.end() // Stäng anslutning
})

Vanliga frågor (FAQ)

Som standard skickar MQTT data i klartext, vilket inte är säkert. Produktionstillämpningar använder dock vanligtvis TLS/SSL för att kryptera anslutningen (MQTTS), oftast på port 8883. Dessutom kan användarnamn/lösenordsautentisering och klientcertifikat användas för att auktorisera enheter på mäklarnivå.

Ett kvarhållet meddelande är ett vanligt MQTT-meddelande med "retained"-flaggan inställd på sant. Mäklaren lagrar det senast kvarhållna meddelandet för det ämnet. När en ny klient prenumererar på det ämnet får den omedelbart det kvarhållna meddelandet. Det är användbart för "statusuppdateringar" (t.ex. att ge den senast kända temperaturen till en enhet som just har vaknat).

LWT är en funktion där en klient anger ett meddelande som automatiskt publiceras av mäklaren om klienten kopplas från oväntat (t.ex. batteriet dör, nätverksfel). Det låter andra klienter veta att en enhet har gått offline oväntat.

Standard-MQTT använder TCP-port 1883. MQTT över SSL/TLS använder port 8883. MQTT över WebSockets använder vanligtvis port 80 eller 443 (om den är säker), eller anpassade portar som 9001 beroende på mäklarens konfiguration.

När en klient ansluter med "Clean Session = false" skapar mäklaren en beständig session. Den sparar alla prenumerationer och köar QoS 1- och 2-meddelanden för klienten medan den är offline. När klienten återansluter får den alla missade meddelanden.
