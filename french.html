La Norme pour la Messagerie IoT

Maîtrisez le protocole MQTT. Une messagerie légère, efficace et fiable pour l'Internet des Objets. Conçu pour les réseaux instables et les environnements à faible bande passante.

Qu'est-ce que MQTT ?

MQTT (Message Queuing Telemetry Transport) est un protocole de messagerie standard OASIS pour l'Internet des Objets (IoT). Il est conçu comme un transport de messagerie publication/abonnement (publish/subscribe) extrêmement léger, idéal pour connecter des appareils distants avec une empreinte de code réduite et une bande passante réseau minimale.

Initialement développé par IBM en 1999 pour surveiller les oléoducs via des connexions satellitaires, il est aujourd'hui devenu la norme de facto pour l'IoT en raison de son efficacité et de sa fiabilité sur des réseaux instables.

Pourquoi est-il si populaire ?

  • ⚡ Léger : La taille minimale du paquet n'est que de 2 octets, ce qui réduit la surcharge du réseau.
  • 🛡️ Fiable : Offre 3 niveaux de Qualité de Service (QoS) pour garantir la livraison.
  • 🔄 Bidirectionnel : Permet la messagerie entre l'appareil et le cloud, et inversement.
  • 💾 Persistant : Les messages conservés (retained messages) permettent aux nouveaux appareils d'obtenir immédiatement le dernier état connu.

Comparaison : MQTT vs HTTP

Bien que HTTP soit la norme du web, il est lourd et centré sur les documents. MQTT est centré sur les données.

Architecture & Composants

Le protocole MQTT découple l'expéditeur (éditeur) et le récepteur (abonné) via un composant central appelé le Broker.

Le Broker

Le cœur du système. Il reçoit tous les messages, les filtre, décide qui y est intéressé en fonction des abonnements, puis publie le message à tous les clients abonnés. Les brokers populaires incluent Mosquitto, HiveMQ et EMQX.

Éditeur (Publisher)

Un client qui envoie des données (messages) au broker sur un sujet (topic) spécifique. Par exemple, un capteur de température publiant des données sur home/livingroom/temp. Les éditeurs n'ont pas besoin de savoir qui sont les abonnés.

Abonné (Subscriber)

Un client qui enregistre un intérêt pour un sujet spécifique. Lorsque le broker reçoit un message sur ce sujet, il le transfère à l'abonné. Un client peut être à la fois éditeur et abonné.

Comprendre les Sujets (Topics)

Les sujets MQTT sont des chaînes hiérarchiques utilisées pour filtrer les messages. Ils utilisent une barre oblique / comme délimiteur. Ils sont sensibles à la casse.

Structure du Sujet

Un sujet typique ressemble à ceci :

myhome / groundfloor / kitchen / temp

Cette hiérarchie permet un adressage spécifique des appareils.

Caractères Génériques (Wildcards)

  • Niveau Unique (+) :
    home/+/temp correspond à home/kitchen/temp mais pas à home/kitchen/fridge/temp.
  • Niveau Multiple (#) :
    home/# correspond à tout ce qui commence par home, par ex. home/kitchen/temp et home/garage/light/status. Cela doit être le dernier caractère du sujet.

Qualité de Service (QoS)

MQTT fournit trois qualités de service spécifiques pour la livraison des messages. Cela permet au concepteur de choisir le bon équilibre entre la surcharge et la fiabilité pour des messages spécifiques.

0

QoS 0

Au plus une fois

Aussi connu sous le nom de "Tirer et oublier" (Fire and forget). Le message est envoyé une fois. Aucune confirmation n'est attendue. Si la connexion est interrompue ou le serveur est occupé, le message est perdu à jamais.

Cas d'utilisation : Données périodiques d'un capteur de température où manquer une lecture sur cent n'est pas critique.

1

QoS 1

Au moins une fois

Garantit qu'un message sera livré au moins une fois au destinataire. L'expéditeur stocke le message jusqu'à ce qu'il reçoive un paquet PUBACK. Des doublons peuvent survenir si l'accusé de réception est perdu.

Cas d'utilisation : Allumer un interrupteur de lumière. Vous voulez absolument qu'il s'allume, et le faire deux fois est acceptable.

2

QoS 2

Exactement une fois

Le niveau le plus sûr et le plus lent. Garantit que le message est reçu exactement une fois en utilisant un processus de vérification (handshake) en quatre étapes. Cela évite les doublons.

Cas d'utilisation : Transactions bancaires, systèmes de facturation ou alarmes critiques où les doublons causent des erreurs.

Exemples d'Implémentation

MQTT dispose de bibliothèques clientes disponibles pour presque tous les langages de programmation (C, C++, Java, Python, Go, JavaScript, etc.).

Python (Paho-MQTT)

La bibliothèque standard pour les applications IoT en Python.

import paho.mqtt.client as mqtt

# Fonction de rappel (callback) lors de la connexion
def on_connect(client, userdata, flags, rc):
    print(f"Connecté avec le code de résultat {rc}")
    # S'abonner dans on_connect garantit 
    # que nous nous réabonnons si nous perdons la connexion
    client.subscribe("home/sensors/#")

# Fonction de rappel lors de la réception d'un message
def on_message(client, userdata, msg):
    print(f"{msg.topic}: {msg.payload.decode()}")

client = mqtt.Client()
client.on_connect = on_connect
client.on_message = on_message

client.connect("broker.hivemq.com", 1883, 60)
client.loop_forever()

JavaScript (Node.js)

Utilisation de la bibliothèque MQTT.js pour les opérations asynchrones.

const mqtt = require('mqtt')
// Se connecter à un broker de test public
const client  = mqtt.connect('mqtt://test.mosquitto.org')

client.on('connect', function () {
  console.log("Connecté !")
  
  // S'abonner au sujet de présence
  client.subscribe('presence', function (err) {
    if (!err) {
      // Publier un message
      client.publish('presence', 'Bonjour mqtt')
    }
  })
})

client.on('message', function (topic, message) {
  // le message est un Buffer
  console.log(message.toString())
  client.end() // Fermer la connexion
})

Foire Aux Questions (FAQ)

Par défaut, MQTT envoie les données en texte brut, ce qui n'est pas sécurisé. Cependant, les implémentations en production utilisent généralement TLS/SSL pour chiffrer la connexion (MQTTS), le plus souvent sur le port 8883. De plus, l'authentification par nom d'utilisateur/mot de passe et les certificats clients peuvent être utilisés pour autoriser les appareils au niveau du broker.

Un message conservé est un message MQTT normal dont l'indicateur "retained" est défini sur vrai (true). Le broker stocke le dernier message conservé pour ce sujet. Lorsqu'un nouveau client s'abonne à ce sujet, il reçoit immédiatement le message conservé. C'est utile pour les mises à jour d'"état" (par exemple, fournir la dernière température connue à un appareil qui vient de s'allumer).

Le LWT est une fonctionnalité où un client spécifie un message qui sera publié automatiquement par le broker si le client se déconnecte de manière inattendue (par ex., batterie épuisée, panne de réseau). Cela permet aux autres clients de savoir qu'un appareil s'est déconnecté de manière imprévue.

Le MQTT standard utilise le port TCP 1883. Le MQTT sur SSL/TLS utilise le port 8883. Le MQTT sur WebSockets utilise généralement le port 80 ou 443 (s'il est sécurisé), ou des ports personnalisés comme 9001 selon la configuration du broker.

Lorsqu'un client se connecte avec "Clean Session = false", le broker crée une session persistante. Il sauvegarde tous les abonnements et met en file d'attente les messages QoS 1 et 2 pour le client pendant qu'il est hors ligne. Lorsque le client se reconnecte, il reçoit tous les messages manqués.
