El estándar para la mensajería IoT

Domine el protocolo MQTT. Mensajería ligera, eficiente y confiable para el Internet de las Cosas. Construido para redes inestables y entornos de bajo ancho de banda.

¿Qué es MQTT?

MQTT (Message Queuing Telemetry Transport) es un protocolo de mensajería estándar de OASIS para el Internet de las Cosas (IoT). Está diseñado como un transporte de mensajería publicación/suscripción extremadamente ligero, ideal para conectar dispositivos remotos con un tamaño de código reducido y un ancho de banda de red mínimo.

Desarrollado inicialmente por IBM en 1999 para monitorear oleoductos a través de conexiones satelitales, ahora se ha convertido en el estándar de facto para IoT debido a su eficiencia y confiabilidad en redes inestables.

¿Por qué es tan popular?

  • ⚡ Ligero: El tamaño de paquete más pequeño es de solo 2 bytes, reduciendo la sobrecarga de la red.
  • 🛡️ Confiable: Ofrece 3 niveles de Calidad de Servicio (QoS) para garantizar la entrega.
  • 🔄 Bidireccional: Permite la mensajería entre dispositivo a la nube y nube al dispositivo.
  • 💾 Persistente: Los mensajes retenidos permiten que los nuevos dispositivos obtengan de inmediato el último estado conocido.

Comparación: MQTT vs HTTP

Mientras que HTTP es el estándar web, es pesado y está centrado en documentos. MQTT está centrado en datos.

Arquitectura y Componentes

El protocolo MQTT desacopla al remitente (editor) y al receptor (suscriptor) a través de un componente central llamado Broker.

El Broker

El corazón del sistema. Recibe todos los mensajes, los filtra, decide quién está interesado en ellos según las suscripciones y luego publica el mensaje a todos los clientes suscritos. Brokers populares incluyen Mosquitto, HiveMQ y EMQX.

Editor (Publisher)

Un cliente que envía datos (mensajes) al broker sobre un tema específico (topic). Por ejemplo, un sensor de temperatura que publica datos en home/livingroom/temp. Los editores no necesitan saber quiénes son los suscriptores.

Suscriptor (Subscriber)

Un cliente que registra interés en un tema en específico. Cuando el broker recibe un mensaje sobre ese tema, lo reenvía al suscriptor. Un cliente puede ser tanto editor como suscriptor.

Comprendiendo los Temas (Topics)

Los temas MQTT son cadenas jerárquicas utilizadas para filtrar mensajes. Usan una barra inclinada / como delimitador. Distinguen entre mayúsculas y minúsculas.

Estructura del Tema

Un tema típico se ve así:

myhome / groundfloor / kitchen / temp

Esta jerarquía permite el direccionamiento específico de dispositivos.

Comodines de Temas (Wildcards)

  • Nivel único (+):
    home/+/temp coincide con home/kitchen/temp pero no con home/kitchen/fridge/temp.
  • Multinivel (#):
    home/# coincide con todo lo que comience con home, ej., home/kitchen/temp y home/garage/light/status. Debe ser el último carácter del tema.

Calidad de Servicio (QoS)

MQTT proporciona tres calidades de servicio específicas para la entrega de mensajes. Esto permite al diseñador elegir el equilibrio adecuado entre la sobrecarga y la confiabilidad para mensajes específicos.

0

QoS 0

Como máximo una vez

También conocido como "Disparar y olvidar". El mensaje se envía una vez. No se espera confirmación. Si la conexión se cae o el servidor está ocupado, el mensaje se pierde para siempre.

Caso de uso: Datos periódicos del sensor de temperatura donde faltar una lectura de cien no es crítico.

1

QoS 1

Al menos una vez

Garantiza que un mensaje será entregado al menos una vez al receptor. El remitente almacena el mensaje hasta que recibe un paquete PUBACK. Pueden ocurrir duplicados si el acuse de recibo se pierde.

Caso de uso: Encender un interruptor de luz. Definitivamente quieres que se encienda, y hacerlo dos veces es aceptable.

2

QoS 2

Exactamente una vez

El nivel más seguro y lento. Garantiza que el mensaje se reciba exactamente una vez mediante un proceso de reconocimiento (handshake) de cuatro pasos. Esto previene los duplicados.

Caso de uso: Transacciones bancarias, sistemas de facturación o alarmas críticas donde los duplicados causan errores.

Ejemplos de Implementación

MQTT tiene bibliotecas de clientes disponibles para casi todos los lenguajes de programación (C, C++, Java, Python, Go, JavaScript, etc.).

Python (Paho-MQTT)

La biblioteca estándar para aplicaciones IoT en Python.

import paho.mqtt.client as mqtt

# Función callback al conectar
def on_connect(client, userdata, flags, rc):
    print(f"Conectado con código de resultado {rc}")
    # Suscribirse en on_connect asegura 
    # que nos volvamos a suscribir si perdemos la conexión
    client.subscribe("home/sensors/#")

# Función callback al recibir un mensaje
def on_message(client, userdata, msg):
    print(f"{msg.topic}: {msg.payload.decode()}")

client = mqtt.Client()
client.on_connect = on_connect
client.on_message = on_message

client.connect("broker.hivemq.com", 1883, 60)
client.loop_forever()

JavaScript (Node.js)

Usando la biblioteca MQTT.js para operaciones asíncronas.

const mqtt = require('mqtt')
// Conectar a un broker público de prueba
const client  = mqtt.connect('mqtt://test.mosquitto.org')

client.on('connect', function () {
  console.log("¡Conectado!")
  
  // Suscribirse al tema presence
  client.subscribe('presence', function (err) {
    if (!err) {
      // Publicar un mensaje
      client.publish('presence', 'Hola mqtt')
    }
  })
})

client.on('message', function (topic, message) {
  // el mensaje es un Buffer
  console.log(message.toString())
  client.end() // Cerrar la conexión
})

Preguntas Frecuentes

De forma predeterminada, MQTT envía datos en texto plano, lo que no es seguro. Sin embargo, las implementaciones de producción suelen usar TLS/SSL para cifrar la conexión (MQTTS), normalmente en el puerto 8883. Además, se puede usar autenticación de nombre de usuario/contraseña y Certificados de Cliente para autorizar dispositivos a nivel del broker.

Un mensaje retenido es un mensaje MQTT normal con la bandera "retained" (retenido) establecida en verdadero. El broker almacena el último mensaje retenido para ese tema. Cuando un nuevo cliente se suscribe a ese tema, recibe inmediatamente el mensaje retenido. Es útil para actualizaciones de "estado" (ej. proporcionar la última temperatura conocida a un dispositivo que acaba de despertar).

LWT (Last Will and Testament) es una característica donde un cliente especifica un mensaje para ser publicado automáticamente por el broker si el cliente se desconecta de manera no controlada (ej. batería agotada, fallo de red). Permite que otros clientes sepan que un dispositivo se ha desconectado inesperadamente.

El estándar MQTT usa el puerto TCP 1883. MQTT sobre SSL/TLS usa el puerto 8883. MQTT sobre WebSockets normalmente usa el puerto 80 o 443 (si es seguro), o puertos personalizados como 9001, dependiendo de la configuración del broker.

Cuando un cliente se conecta con "Clean Session = false", el broker crea una sesión persistente. Guarda todas las suscripciones y pone en cola los mensajes QoS 1 y 2 para el cliente mientras está desconectado. Cuando el cliente se vuelve a conectar, recibe todos los mensajes perdidos.
