Стандарт обміну повідомленнями для IoT

Опануйте протокол MQTT. Легкий, ефективний та надійний обмін повідомленнями для Інтернету речей. Створений для нестабільних мереж та середовищ з низькою пропускною здатністю.

Запустити симулятор

Що таке MQTT?

MQTT (Message Queuing Telemetry Transport) — це стандартний протокол обміну повідомленнями OASIS для Інтернету речей (IoT). Він розроблений як надзвичайно легкий транспорт за шаблоном публікація/підписка (publish/subscribe), який ідеально підходить для підключення віддалених пристроїв з невеликим обсягом коду та мінімальною пропускною здатністю мережі.

Спочатку розроблений IBM у 1999 році для моніторингу нафтопроводів через супутникові з'єднання, зараз він став стандартом де-факто для IoT завдяки своїй ефективності та надійності у нестабільних мережах.

Чому він такий популярний?

  • ⚡ **Легкий:** Мінімальний розмір пакета становить лише 2 байти, що знижує мережеве навантаження.
  • 🛡️ **Надійний:** Пропонує 3 рівні якості обслуговування (QoS) для гарантії доставки.
  • 🔄 **Двонаправлений:** Дозволяє обмінюватися повідомленнями від пристрою до хмари та від хмари до пристрою.
  • 💾 **Постійний (Persistent):** Збережені (retained) повідомлення дозволяють новим пристроям негайно отримувати останній відомий стан.

Порівняння: MQTT проти HTTP

Тоді як HTTP є веб-стандартом, він важкий та орієнтований на документи. MQTT натомість орієнтований на дані.

Архітектура та компоненти

Протокол MQTT розділяє відправника (видавця) та одержувача (підписника) через центральний компонент, який називається Брокером.

Брокер (Broker)

Серце системи. Він отримує всі повідомлення, фільтрує їх, вирішує, хто в них зацікавлений на основі підписок, а потім публікує повідомлення для всіх підписаних клієнтів. Популярні брокери: Mosquitto, HiveMQ та EMQX.

Видавець (Publisher)

Клієнт, який відправляє дані (повідомлення) брокеру в певний топік. Наприклад, датчик температури, що публікує дані в dim/vitalnya/temp. Видавцям не потрібно знати, ким є підписники.

Підписник (Subscriber)

Клієнт, який реєструє інтерес до певного топіка. Коли брокер отримує повідомлення в цей топік, він пересилає його підписнику. Один клієнт може бути одночасно і видавцем, і підписником.

Розуміння топіків (Topics)

Топіки MQTT — це ієрархічні рядки, що використовуються для фільтрації повідомлень. Як роздільник у них використовується скісна риска /. Топіки чутливі до регістру.

Структура топіка

Типовий топік виглядає так:

miydim / 1poverh / kuhnya / temp

Ця ієрархія дозволяє точно адресувати пристрої.

Символи підстановки (Wildcards)

  • Один рівень (+):
    dim/+/temp відповідає dim/kuhnya/temp, але не dim/kuhnya/holodylnyk/temp.
  • Багато рівнів (#):
    dim/# відповідає всьому, що починається з "dim", наприклад, dim/kuhnya/temp та dim/garazh/svitlo/status. Цей символ має бути останнім у топіку.

Якість обслуговування (QoS)

MQTT надає три визначені рівні якості обслуговування для доставки повідомлень. Це дозволяє розробнику вибрати правильний баланс між мережевими витратами та надійністю для конкретних повідомлень.

0

QoS 0

Не більше одного разу

Також відомо як "Відправив і забув" (Fire and forget). Повідомлення надсилається один раз. Підтвердження не очікується. Якщо з'єднання обривається або сервер зайнятий, повідомлення втрачається назавжди.

Сценарій: Періодичні дані датчика температури, де пропуск одного показання зі ста не є критичним.

1

QoS 1

Щонайменше один раз

Гарантує, що повідомлення буде доставлено одержувачу як мінімум один раз. Відправник зберігає повідомлення, поки не отримає пакет PUBACK. Якщо підтвердження втрачено, можуть виникати дублікати.

Сценарій: Увімкнення вимикача світла. Ви точно хочете, щоб він увімкнувся, і відправка команди двічі є цілком припустимою.

2

QoS 2

Рівно один раз

Найбезпечніший та найповільніший рівень. Гарантує, що повідомлення буде отримано рівно один раз завдяки чотирьохетапному "рукостисканню". Це запобігає дублюванню.

Сценарій: Банківські транзакції, білінгові системи або критично важливі тривоги, де дублікати викликають помилки.

Приклади реалізації

Для MQTT існують клієнтські бібліотеки практично під кожну мову програмування (C, C++, Java, Python, Go, JavaScript тощо).

Python (Paho-MQTT)

Стандартна бібліотека для IoT-додатків на Python.

import paho.mqtt.client as mqtt

# Функція зворотного виклику при підключенні
def on_connect(client, userdata, flags, rc):
    print(f"Підключено з кодом результату {rc}")
    # Підписка в on_connect гарантує, 
    # що ми перепідпишемося при втраті з'єднання
    client.subscribe("dim/datchyky/#")

# Функція зворотного виклику при отриманні повідомлення
def on_message(client, userdata, msg):
    print(f"{msg.topic}: {msg.payload.decode()}")

client = mqtt.Client()
client.on_connect = on_connect
client.on_message = on_message

client.connect("broker.hivemq.com", 1883, 60)
client.loop_forever()

JavaScript (Node.js)

Використання бібліотеки MQTT.js для асинхронних операцій.

const mqtt = require('mqtt')
// Підключення до публічного тестового брокера
const client  = mqtt.connect('mqtt://test.mosquitto.org')

client.on('connect', function () {
  console.log("Підключено!")
  
  // Підписка на топік присутності
  client.subscribe('presence', function (err) {
    if (!err) {
      // Публікація повідомлення
      client.publish('presence', 'Pryvit mqtt')
    }
  })
})

client.on('message', function (topic, message) {
  // message є об'єктом Buffer
  console.log(message.toString())
  client.end() // Закриття з'єднання
})

Поширені запитання (FAQ)

За замовчуванням MQTT передає дані у вигляді відкритого тексту, що є небезпечним. Однак виробничі реалізації зазвичай використовують TLS/SSL для шифрування з'єднання (MQTTS), як правило, на порту 8883. Крім того, на рівні брокера для авторизації пристроїв може застосовуватися автентифікація за іменем користувача/паролем та клієнтські сертифікати.

Утримане повідомлення — це звичайне MQTT-повідомлення з прапорцем "retained", встановленим у true. Брокер зберігає останнє утримане повідомлення для цього топіка. Коли новий клієнт підписується на цей топік, він негайно отримує дане повідомлення. Це корисно для оновлень "статусу" (наприклад, надання останньої відомої температури пристрою, який щойно вийшов із режиму сну).

LWT — це функція, за якої клієнт задає повідомлення, яке буде автоматично опубліковано брокером, якщо клієнт відключиться некоректно (наприклад, сяде батарея, станеться збій мережі). Це дозволяє іншим клієнтам дізнатися, що пристрій несподівано перейшов у автономний режим.

Стандартний MQTT використовує TCP-порт 1883. MQTT поверх SSL/TLS використовує порт 8883. MQTT через WebSockets зазвичай використовує порти 80 або 443 (якщо безпечно), або нестандартні порти, наприклад 9001, залежно від конфігурації брокера.

Коли клієнт підключається з параметром "Clean Session = false", брокер створює постійну сесію. Він зберігає всі підписки та ставить у чергу повідомлення QoS 1 та 2 для клієнта, поки той перебуває в автономному режимі. Коли клієнт підключається знову, він отримує всі пропущені повідомлення.
