O Padrão para Mensagens IoT

Domine o protocolo MQTT. Mensagens leves, eficientes e confiáveis para a Internet das Coisas. Criado para redes instáveis e ambientes de baixa largura de banda.

O que é MQTT?

MQTT (Message Queuing Telemetry Transport) é um protocolo de mensagens padrão OASIS para a Internet das Coisas (IoT). É projetado como um transporte de mensagens publicar/assinar extremamente leve que é ideal para conectar dispositivos remotos com um pequeno código e largura de banda de rede mínima.

Desenvolvido inicialmente pela IBM em 1999 para monitorar oleodutos sobre conexões de satélite, agora se tornou o padrão de fato para IoT devido à sua eficiência e confiabilidade em redes instáveis.

Por que é tão popular?

  • ⚡ Leve: O menor tamanho de pacote é de apenas 2 bytes, reduzindo a sobrecarga da rede.
  • 🛡️ Confiável: Oferece 3 níveis de Qualidade de Serviço (QoS) para garantir a entrega.
  • 🔄 Bidirecional: Permite mensagens entre dispositivo-para-nuvem e nuvem-para-dispositivo.
  • 💾 Persistente: Mensagens retidas permitem que novos dispositivos obtenham imediatamente o último estado conhecido.

Arquitetura e Componentes

O protocolo MQTT separa o remetente (publicador) e o receptor (assinante) por meio de um componente central chamado Broker.

O Broker

O coração do sistema. Ele recebe todas as mensagens, as filtra, decide quem está interessado nelas com base nas assinaturas e, em seguida, publica a mensagem para todos os clientes assinantes. Brokers populares incluem Mosquitto, HiveMQ e EMQX.

Publicador (Publisher)

Um cliente que envia dados (mensagens) ao broker em um tópico específico. Por exemplo, um sensor de temperatura publicando dados em casa/saladeestar/temp. Os publicadores não precisam saber quem são os assinantes.

Assinante (Subscriber)

Um cliente que registra interesse em um tópico específico. Quando o broker recebe uma mensagem nesse tópico, ele a encaminha para o assinante. Um cliente pode ser tanto publicador quanto assinante.

Entendendo os Tópicos

Os tópicos MQTT são strings hierárquicas usadas para filtrar mensagens. Eles usam uma barra / como delimitador. Eles diferenciam maiúsculas de minúsculas.

Estrutura do Tópico

Um tópico típico se parece com isto:

minhacasa / terreo / cozinha / temp

Esta hierarquia permite o endereçamento específico de dispositivos.

Curingas de Tópico (Wildcards)

  • Nível Único (+):
    casa/+/temp corresponde a casa/cozinha/temp, mas não a casa/cozinha/geladeira/temp.
  • Multinível (#):
    casa/# corresponde a tudo que começa com casa, por exemplo, casa/cozinha/temp e casa/garagem/luz/status. Deve ser o último caractere no tópico.

Qualidade de Serviço (QoS)

O MQTT fornece três qualidades específicas de serviço para a entrega de mensagens. Isso permite que o designer escolha o equilíbrio certo entre a sobrecarga de rede e a confiabilidade para mensagens específicas.

0

QoS 0

No máximo uma vez

Também conhecido como "Dispare e esqueça" (Fire and forget). A mensagem é enviada uma vez. Nenhuma confirmação é esperada. Se a conexão cair ou o servidor estiver ocupado, a mensagem se perde para sempre.

Caso de uso: Dados periódicos de sensores de temperatura em que perder uma leitura de cem não é crítico.

1

QoS 1

Pelo menos uma vez

Garante que uma mensagem será entregue pelo menos uma vez ao receptor. O remetente armazena a mensagem até obter um pacote PUBACK. Mensagens duplicadas podem ocorrer se a confirmação for perdida.

Caso de uso: Ligar o interruptor de uma luz. Você definitivamente quer que ela ligue, e fazer isso duas vezes é aceitável.

2

QoS 2

Exatamente uma vez

O nível mais seguro e mais lento. Garante que a mensagem seja recebida exatamente uma vez usando um handshake de quatro etapas. Isso evita duplicações.

Caso de uso: Transações bancárias, sistemas de cobrança ou alarmes críticos onde duplicatas causam erros.

Exemplos de Implementação

O MQTT possui bibliotecas de cliente disponíveis para quase todas as linguagens de programação (C, C++, Java, Python, Go, JavaScript, etc.).

Python (Paho-MQTT)

A biblioteca padrão para aplicações IoT em Python.

import paho.mqtt.client as mqtt

# Callback ao conectar
def on_connect(client, userdata, flags, rc):
    print(f"Conectado com o código de resultado {rc}")
    # Assinar em on_connect garante que 
    # reassinaremos se perdermos a conexão
    client.subscribe("casa/sensores/#")

# Callback quando a mensagem é recebida
def on_message(client, userdata, msg):
    print(f"{msg.topic}: {msg.payload.decode()}")

client = mqtt.Client()
client.on_connect = on_connect
client.on_message = on_message

client.connect("broker.hivemq.com", 1883, 60)
client.loop_forever()

JavaScript (Node.js)

Usando a biblioteca MQTT.js para operações assíncronas.

const mqtt = require('mqtt')
// Conecta a um broker de teste público
const client  = mqtt.connect('mqtt://test.mosquitto.org')

client.on('connect', function () {
  console.log("Conectado!")
  
  // Assina o tópico de presença
  client.subscribe('presenca', function (err) {
    if (!err) {
      // Publica uma mensagem
      client.publish('presenca', 'Ola mqtt')
    }
  })
})

client.on('message', function (topic, message) {
  // a mensagem é um Buffer
  console.log(message.toString())
  client.end() // Fecha a conexão
})

Perguntas Frequentes (FAQ)

Por padrão, o MQTT envia dados em texto simples, o que não é seguro. No entanto, as implementações de produção normalmente usam TLS/SSL para criptografar a conexão (MQTTS), normalmente na porta 8883. Além disso, a autenticação de nome de usuário/senha e os Certificados de Cliente podem ser usados para autorizar dispositivos no nível do broker.

Uma mensagem retida é uma mensagem MQTT normal com a flag "retained" definida como verdadeira (true). O broker armazena a última mensagem retida para aquele tópico. Quando um novo cliente assina esse tópico, ele recebe imediatamente a mensagem retida. É útil para atualizações de "status" (por exemplo, fornecer a última temperatura conhecida a um dispositivo que acabou de despertar).

LWT é um recurso onde um cliente especifica uma mensagem a ser publicada automaticamente pelo broker se o cliente se desconectar abruptamente (por exemplo, bateria acaba, falha na rede). Isso permite que outros clientes saibam que um dispositivo ficou offline inesperadamente.

O MQTT padrão usa a porta TCP 1883. MQTT sobre SSL/TLS usa a porta 8883. MQTT sobre WebSockets geralmente usa a porta 80 ou 443 (se seguro), ou portas personalizadas como 9001, dependendo da configuração do broker.

Quando um cliente se conecta com "Clean Session = false", o broker cria uma sessão persistente. Ele salva todas as assinaturas e enfileira as mensagens de QoS 1 e 2 para o cliente enquanto ele está offline. Quando o cliente se reconecta, ele recebe todas as mensagens perdidas.
